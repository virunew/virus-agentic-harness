Agentic coding: from hype to harness

What goes wrong when agents write the code, and a working method that answers each failure.

Opening

Agents made the first week fast. They did not make the project finish.

This talk comes from more than two years of LLM-assisted and then agentic coding. It includes projects that were scrapped after months of steady effort. It also includes constant switching to the newest tools and methods, hoping the next one would fix the problem.

The tools were not the problem. The way the work was organized around them was. The rest of this talk is what was learned the hard way: what people believe about agentic coding, what actually goes wrong, and the method that now keeps it from going wrong.

The one-line thesis An agent is a team of strong, fast horses. Without a harness they run in every direction. The method is the harness, and the reins stay in the developer's hands.

Part 1 · Misconceptions

The beliefs are built on real first impressions

A prototype in an afternoon

An agent can produce a working demo very quickly. That moment is genuinely impressive, and it becomes the reference point for everything that follows.

Fast changes, for a while

For the first weeks it absorbs change requests quickly. The codebase is still small enough for the agent to hold in its head.

Vendor narrative

Model and tool vendors market the best case. Demos are greenfield, short, and chosen to succeed.

Each of these is true. The mistake is extrapolating from them to a large, long-lived codebase that a team has to own.

Part 1 · Misconceptions

Four beliefs, and what actually happens

Belief

Code is cheap now.

Reality

Code that comes cheap only goes so far. Writing it is cheap. Owning it is not: reviewing, reworking, and eventually scrapping it. Months of effort were lost this way.

Belief

We will double or triple our output.

Reality

That holds for prototypes and small projects. On mature work, measured speed can go down while people feel faster.

Belief

Agents will work in every situation.

Reality

Large codebases bring diminishing returns. The agent lacks the unwritten knowledge that lives in the team's heads.

Belief

Agents work equally well with any technology.

Reality

Agents are only as good as their training data. Closed-source, niche, or new technology with sparse public code gets weaker, more invented answers.

Part 1 · Misconceptions

Feeling faster is not being faster

METR ran a randomized controlled trial in early 2025. Sixteen experienced developers did 246 real tasks in their own large open-source repositories (about a million lines of code each). Each task was randomly allowed or not allowed to use AI tools.

24%
Speed-up the developers predicted before starting
20%
Speed-up they believed they got, after finishing
19% slower
What was measured, when AI was allowed

The time went into prompting, waiting, reviewing, and correcting output. Developers reported that the size and age of the codebase limited how much the agent could help. It could not use the tacit knowledge they carried.

A separate study of open-source projects after Copilot adoption (Tilburg University) found output went up, driven by less-experienced contributors. That code needed more rework. Core maintainers reviewed 6.5% more code, and their own original output fell by 19%.

METR study, in full: Joel Becker, Nate Rush, Beth Barnes, David Rein. "Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity". Model Evaluation & Threat Research (METR), 10 July 2025. arXiv 2507.09089. Blog post · Paper (PDF). Design: a randomized controlled trial run February to June 2025. 16 experienced developers, with about 5 years each on their own project, did 246 real tasks: bug fixes, features, and refactors, averaging about 2 hours each. The repositories averaged 22k+ GitHub stars and 1M+ lines of code. Each task was randomly assigned to allow or forbid AI tools. When AI was allowed, developers mostly used Cursor Pro with Claude 3.5/3.7 Sonnet. Screens were recorded, and developers were paid $150 an hour. Results:
  • Developers forecast a 24% speed-up beforehand, and estimated 20% afterwards.
  • Economics experts predicted 39% faster, and ML experts 38% faster.
  • Measured: 19% slower when AI was allowed.
METR examined 20 factors that could explain the slowdown and found no single cause. With AI, developers spent less time coding and searching. They spent more time prompting, waiting on and reviewing AI output, and idle. METR calls the result a snapshot of early-2025 tools in one setting: mature, high-standard codebases that the developers know well.
Also cited: Xu et al., "AI-Assisted Programming Decreases the Productivity of Experienced Developers by Increasing the Technical Debt and Maintenance Burden", arXiv 2510.10165. Both are snapshots of specific settings and tools, not a verdict on all software work.

Part 2 · Challenges

Control slips away quietly, because the output looks good

Hidden decisions

Every response has dozens of small choices inside it: a default value, a fallback, a new dependency, a renamed field. None of them are announced. Together they become the architecture.

Option overload

Asked for an approach, the agent offers four. They all sound reasonable. Few people read all four carefully, so the choice is made on the first paragraph.

Reading stops

After enough good results, developers skim, then stop reading. That is exactly when the first serious mistake gets in.

Speed pressure

The agent writes faster than a person can review. Managers see the speed and expect outcomes at the same pace. Review is the first thing cut.

Part 2 · Challenges

The agent forgets, varies, and writes what it has seen most

Memory

Everything it knows about your project lives in the current context. A new session starts nearly blank. In a long context, instructions in the middle fade, and one task in a list of ten gets dropped.

Consistency

Ask the same question twice and you get two different designs. Without a written decision, each session re-decides.

Familiar patterns

It reproduces the most common patterns in its training data, good and bad. A new pattern your team chose has to be taught every time.

Complexity and duplication

It writes a fresh implementation instead of finding the existing one. It adds defensive branches, options, and fallbacks for cases nobody asked about.

Part 2 · Challenges · The central one

Understanding is the new bottleneck

Agents write code faster than people can absorb it. The quiet failure is not bad code. It is code the team no longer understands.

Understand to verify

The first reason: check the agent's work. Does it match the spec? Is it well built? That is a yes-or-no question, and agents are getting better at answering it themselves.

Understand to participate

The stronger reason: a project is many loops with the agent, not one. Your understanding of the system is where the next good idea comes from. Without it you can only approve, not steer.

Cognitive debt Cognitive debt is like technical debt, but for understanding. You can skip understanding in the short term, and it bites later. That is the point where a team scraps a codebase, because nobody can safely change it.
What it feels like: Charlie Chaplin on the assembly line The line speeds up, and the worker can no longer keep up with the bolts coming at him. That is a developer reviewing a coding agent's output.
Part 3 · The method

Seven principles behind the method

1. Simplicity, above every other rule

The smallest readable change that does what was asked. Anything more is a question to the developer, not a surprise in the diff.

2. All decisions are ours

Including the small ones. The agent proposes. The developer decides. The decision is written down with its reason.

3. Written memory, not chat memory

Plans, decisions, learnings, and git history are the record. A new session reads them, not the old conversation.

4. TDD: test-driven development

Write the test first and watch it fail (red). Write the least code that makes it pass (green). Then tidy up while it stays green (refactor).

Why it helps with agents: the test pins down what "done" means before the agent writes code. It catches confident but wrong output, and stops a later session from quietly changing behavior. It also fences out extra code: anything no test asks for is a candidate to cut.

5. A different model reviews

The model that wrote the plan or code is not the only one that reviews it. Then a human vets the review.

6. A hawk's eye on the agent

The developer watches what the agent does and reviews while it works. The full picture of the system stays in the developer's head.

7. The method evolves

Recurring problems change the workflow. New tools are tried carefully before they are adopted.

The harnessPrinciples 1 to 7 are written into files every agent reads before it works. That written set is the harness.

Part 3 · The method

Six highlights worth knowing before the details

Grill before planning

The agent asks one question at a time until every open branch of the design is closed. Settled decisions are never asked again.

The ExecPlan

A living, self-contained plan a cold agent can finish alone. It has a progress checklist, a decision log, discoveries, and an observable acceptance test.

One goal per plan

If a plan spans several separately shippable outcomes, split it. Small plans can be reviewed and finished.

Test-first, explained

Red, green, refactor. The agent states what each test proves, why that layer, the command, and the failure it saw.

Cross-model review, then vet

A different model reviews plans and code. A human then accepts or rejects each comment against the project rules.

Compounding knowledge

Learnings, decisions, and a shared glossary make each next task easier. The rule files are pruned so they stay short.

Part 4 · Answers · A. Control

A hawk's eye: what to watch while the agent works

Waiting for the agent is review time. These signals mean something slipped through:

In the diff
  • Files outside the plan's scope changed
  • A new dependency, default value, or fallback appeared
  • A test was weakened or deleted so it would pass
  • A second version of something that already exists
In the conversation
  • A choice made in prose but missing from the Decision Log
  • "Done" claimed without a command and its output
  • The same fix tried twice without a new diagnosis
  • Tests run against anything other than the test environment
The full view stays with the developer Developers read and approve every plan, and own the architecture notes. The code map exists to orient people, not only agents. The goal is that the developer can still explain the whole system without asking the agent.
Part 4 · Answers · The understanding gap

Ways to understand code beyond reading the diff line by line

1. Explainers for every change

When the agent finishes, it writes an explanation, not just a diff:

  • Background first: what was already there before the change
  • Intuition before details: the goal and key concepts before any code
  • A literate diff: changes in a sensible order, as prose with code snippets

Read the explainer first, then the diff.

2. A quiz as a speed regulator

The explainer ends with about five questions about the change. The rule: do not send the code on, or approve someone else's, until you pass.

Reading is easy to fake to yourself. The quiz checks that you understood it, so the loop cannot run faster than your understanding.

3. Micro-worlds

Have the agent build small tools you can play with: a step-through debugger, a visual before-and-after of a migration, or an interactive figure.

This applies Seymour Papert's idea that people learn best by living inside the subject. Agents can write code that helps people understand other code.

4. Shared spaces

A team needs to understand together. A shared mental model and vocabulary allow fast, creative conversation. Keep explainers where the team discusses them, not in one person's chat.

Where this lives in the method Hawk's eyeTest-firstCode reviewGlossaryTeam workflow
An explain-diff skill turns each finished change into an explainer with a quiz. The agent must explain every test it writes. Plans and decision logs are written for a newcomer. The glossary provides the shared vocabulary. The goal is to augment the developer, not just to automate.

Part 4 · Answers · E. Team and cost

Agentic coding economy guidelines

Right-size the work

A direct answer for a one-step change. A short brief for bounded work. A full plan only when the work earns it. Simplicity saves money as well as code.

Context is the bill

Always-loaded rule files are paid for on every turn. Prune them. Load detail only when a step needs it.

Match the model to the job

Use lighter, cheaper models for search and exploration sub-agents. Use the strongest model for planning and review decisions, where quality matters most.

Stop rediscovery

Search past learnings and decisions before solving. A problem solved twice is paid for twice.

Break loops early

If the same fix fails twice, stop and diagnose the root cause instead of asking for a third try.

Review where the risk is

Use the full multi-reviewer, cross-model pass for risky changes such as data, contracts, and security. A light review is enough for low-risk edits.

Measure cost per finished, verified plan, not per token or per prompt.

Keeping it alive

The method keeps learning

Hunt recurring issues

When the same kind of mistake shows up twice, change the workflow, not just the code:

  • write a learning when the code alone will not teach it
  • add or tighten a rule in the policy files
  • review finished sessions for wrong turns and wasted searches
  • prune rules that no longer pull their weight
Adopt new methods carefully

Keep watching for new tools and methods, but trial a promising one thoroughly before going full steam.

  • use it on one contained plan first
  • record what it fixed and what it broke
  • adopt it, adapt it, or drop it, in writing

Example in progress: a persistent issue tracker built for coding agents, being trialled as a longer-term memory for tasks.

Maintaining the harness Prune the always-loaded rule files first. Then update skills from upstream without losing local changes. Then keep each rule in one place, linked from the rest.

Close

Agents are not the problem, and they are not the solution. The harness is.

The decisions stay ours. We understand what was built before it ships. Memory is written down. Every step is checked by a test, a second model, or a person. Simplicity wins every tie.
